# Analytics R1–R7 local readiness fixes — 2026-10-27

Status: implemented locally; deployment remains on hold for the live evidence below. No production migrations, backend/worker releases, tracking flags, client builds, paid services or analytics resets were executed. Existing embedded players, Creator Studio changes, app identifiers and Android configuration are preserved.

## Resolutions

- **R1:** General measurement recovery now runs independently of client collection flags. Previously consenting devices retain disable controls, including stopping account measurement when the device itself is paused. Recovery journals contain account scope and decreasing booleans, never credentials or a new measurement identifier. Offline changes remain pending until server confirmation. Partial decreases retain device consent only when explicitly already active. Preferences GET returns actual self-only settings with private/no-store caching during shutdown. PUT delegates shutdown-safe decreases to the locked RPC; any increase requires the latest expected revision and enabled server collection. Decrease-only replays clamp against current permissions, so a delayed partial withdrawal cannot undo a later full withdrawal. No-op requests preserve revision; repeated decreases still erase optional linkage. HTTP requests and response bodies have ten-second deadlines and actual abort signals; the write RPC has eight-second statement/two-second lock settings.
- **R2:** Every legacy merchant click uses the consent-aware RPC. The engagement RPC checks live consent/revision regardless of context-header presence. Missing, invalid, old or globally disabled context cannot attach merchant actors/sessions. Navigation, anonymous click counts, event dedupe and business membership remain intact. Separate-connection tests cover merchant writes racing withdrawal in both stores.
- **R3:** Both early erasure triggers observe `account_status` and `deleted_at`, with an idempotent deletion predicate. `deleted_at` alone clears optional actor/session linkage, search correlations, general consent and purpose profiles, and invokes the existing business-account deletion cleanup/reconciliation. Restoring the user row restores no consent or erased history. Normal and hard-deletion cases remain covered.
- **R4:** Privacy maintenance has its own loop and busy guard, independent of creator/admin/profile computation. Failed/hung calls are bounded by a real Supabase abort signal plus a scheduling deadline; retries cannot overlap within a loop. Worker RPCs have scoped twenty-second statement and two-second lock settings; HTTP deadlines are twenty-five seconds. No shared database-role defaults are changed. Independent retention can expire data before failed rollups recover: preserve privacy TTL, expose coverage gaps, and alert on worker failure rather than extending retention silently.
- **R5:** Missing projections initialize from existing mirrors, preserving legacy totals. A private nonnegative baseline records the difference between each cumulative mirror and surviving historical facts; it does not manufacture events or backfill period charts. Stock counters must match authoritative current relationships. Inconsistent mirrors/projections, negative/changed baselines and stock disagreement fail the write transaction, including its fact/edge insertion. Indexed counter lookups, a read-only inventory/preflight and an explicit preserving preparation RPC support cutover. Nothing invokes preparation automatically. See the cutover and reset assessment below.
- **R6:** The notification load fixture uses supported `normal` priority, mutable materializer numbers are explicitly numeric, existing theme comparisons are type-correct with the selected appearance unchanged, and the optional collection ID is normalized to null. The already locked SDK-compatible `expo-file-system` 19.0.24 is now a direct dependency; its existing installation was hoisted with the offline/ignore-scripts workflow. No native dependency installation/build was run. Client and backend have separate no-emit check commands.
- **R7:** Cold auth restoration and ordinary foreground refresh pause rather than purge. Unavailable verification holds only a bounded, unexpired cache matching the same account and valid local revision (or the opted-in guest scope). No new observations, session IDs or uploads occur while held, including shutdown. Explicit withdrawal/pending withdrawal, identity/revision mismatch, unknown policy, invalid receipt and expiry discard the queue. Late acknowledgements cannot change a newer generation. Actual account switches/logout retain the explicit purge behavior.

All steps below require future deployment approval. Optional flags off do **not** pause Phase 1 operational engagement writers.

1. Verify target migration history and a restorable backup. These six staged migrations are unpublished; if any equivalent phase has already been applied, prepare reviewed forward migrations rather than editing deployed history.
2. Pause engagement mutation entry points and drain every old/new backend, retry queue, in-flight transaction and legacy/direct counter writer. Include background counter writers and account-deletion transactions. Record the boundary; never run mixed old/new writers. Do not disable privacy recovery for an extended interval.
3. Rehearse the staged migrations on representative isolated full-schema data with the actual roles and PostgREST. The minimal local fixtures are insufficient evidence of deployed compatibility or index cost.
4. Inspect `engagement_counter_preflight()` and the server-only `engagement_counter_inventory`. Inventory covers collection views/shares/product clicks/saves, creator followers/shares, user following and catalog merchant clicks. `blocking_drift` must be zero. Missing projections/baselines are preparable; disagreements are **not** repaired automatically. Preserve relevant before/after totals and relationship row counts without logging private user rows.
5. With writers still drained, run `engagement_prepare_counter_baselines()` in the approved transaction. It locks the relevant tables and initializes only missing baselines/projections. A failed guard rolls the whole transaction back. It changes no existing mirror, fact, membership, cart, user, collection, content or business record. Repeat invocation is safe after parity. Expect zero blocking drift, missing projections and missing baselines afterwards.
6. Verify reconciliation and representative exact totals, then release only compatible atomic writers. Resume entry points after confirmation; monitor drift/write failures. Old non-atomic writers are not a safe rollback target. Keep additive schema and privacy support, then use a forward fix if needed.

The fresh-baseline boundary is a clean **accounting epoch**, without discarding old analytics. Existing mirrors can be higher than surviving fact counts; that difference is retained as a labeled legacy offset. Existing mirror totals below facts, stock disagreements or nonzero projection disagreement need live investigation and an approved decision. The implementation intentionally stops rather than guessing historical truth.

## Optional analytics reset/purge assessment — proposal only

A clean analytics epoch **can** simplify an ambiguous historical cumulative baseline. It does not eliminate write-drain, business-stock parity, migration, privacy or role checks. With the preserving initializer now available, a purge is unnecessary when preflight passes. The recommended default is preservation; first inspect live aggregate parity. No reset SQL or reset endpoint was added or executed.

If live history is irreconcilable and the owner explicitly accepts losing old analytics, the smallest candidate reset is an allowlisted reset at a recorded UTC epoch, restricted to pre-epoch analytics-only data:

- Remove only engagement facts with `(object_type='collection' AND interaction_type IN ('view','impression','share'))`, `(object_type='creator' AND interaction_type='share')`, or `(object_type='catalog_product' AND interaction_type='merchant_click')`, with `created_at < epoch`. Retain any row referenced by an authoritative business obligation; never cascade. Stop to review such references before approval.
- Reset only matching analytics totals: collection `views_count`, `shares_count`, `product_clicks_count`; creator `shares` and catalog-product `merchant_clicks` projections; matching cumulative baseline entries. Do not touch collection `saves_count`, creator `followers_count`, user `following_count`, or any relationship state. Drained writers ensure no post-epoch increments are accidentally zeroed. Initialize stock projections from verified current relationships without deleting those relationships or their facts.
- A purge of `product_clicks` is optional and separate: only pre-epoch click rows proven to be analytics-only and unneeded for contractual/financial attribution could be included. Otherwise retain them under their existing business policy and do not use them to backfill the new analytics epoch. Never clear purchases, orders, payouts or any other business record.
- At this initial release, newly introduced optional raw events, rollups, ledgers, windows and interest tables should have no production data. Verify that assumption first. If already populated, this proposal is insufficient: changing underlying facts while retaining their existing aggregate contributions would be inconsistent. Stop and review a bounded epoch-aware reaggregation/erasure plan; do not truncate all analytics tables as a shortcut.

**Exactly what an approved allowlisted purge would lose:** the old selected fact rows and their event IDs, timestamps, historical view/impression/share/merchant-click history, creator/product attribution, dedupe history and any optional actor/session context still on those rows; old lifetime totals for the named cumulative counters; the ability to reconstruct pre-epoch period metrics from those facts. If separately approved, selected legacy `product_clicks` rows would also lose their click timestamps/context/attribution. Retries of purged event IDs would lose their prior dedupe protection, so old requests must be drained/expired before reopening. Reports must label the new epoch and leave earlier dates unknown, not claim zero activity.

**Retained:** users/auth/accounts, videos/collections/products/places, published and draft content, saves/unsaves, follows/unfollows, likes/unlikes, all current relationships, cart/Stash/place saves, imports/ingests/jobs, notification state, purchases/orders/payouts and other authoritative transactions, environment/credentials, app identifiers and platform configuration. Deleting historical analytics cannot be substituted for consent/erasure recovery. Any additional dataset or field is outside this proposal and requires review.
