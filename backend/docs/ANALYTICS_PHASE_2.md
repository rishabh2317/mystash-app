# Analytics Phase 2 — interaction measurement, local only

Deployment-readiness follow-up: [R1–R7 local fixes and current cutover gates](./ANALYTICS_READINESS_FIXES.md). This supersedes earlier compiler-baseline and maintenance-ordering notes; no production deployment/reset is authorized.

## Scope revision and phase boundaries

This document supersedes the playback portions of the earlier analytics architecture. YouTube Shorts and Instagram Reels are third-party embeds. Playback positions/durations, completion, skips, replays, playback sessions/checkpoints, player observers, and their charts or recommendation features are excluded from Phase 2 **and Phases 3–5**. No playback properties are accepted by the new event contract.

The unshipped playback accumulator, hook, SDK observer, player refs, callbacks, and instrumentation imports were isolated and removed. YouTubeReelItem, InstagramReelItem, CollectionMediaReference, ReelItem, the YouTube HTML helper, and the Product Page's embedded-player function retain their pre-analytics implementation. Product-page open measurement remains outside the player. Existing player diagnostics and playback controls are unchanged.

Phase 2 adds no creator dashboard redesign, admin dashboard, interest-profile computation, or recommendation changes. Stop and report after this phase. Phase 3 will use interaction metrics only; Phase 4 will add operational/business aggregates; Phase 5 will use separately opted-in entity interests without playback signals. The consolidated deployment checklist is due after Phase 5. No production migrations, backend deployments, flag activation, paid services or native builds are authorized now.

## Collection and privacy

Three gates are independent: `EXPO_PUBLIC_ANALYTICS_ENABLED` (client build flag), `ANALYTICS_ENABLED` (server collection flag), and explicit measurement consent. Both flags default false. Neither environment files nor production settings were changed. `ANALYTICS_MAINTENANCE_ENABLED` separately controls retention, so a future collection kill switch need not disable cleanup. Keep all three off until the coordinated release.

Settings reuse the shared toggle/section components. Usage measurement is optional and off by default. Account activity is a second opt-in, requiring usage measurement. Personalization remains off with no profile consumer in this phase. A matching device consent receipt is required even when the account has opted in elsewhere. Consent revisions invalidate queued observations after withdrawal/regrant. Offline withdrawals stop local collection, purge the queue, and persist a pending preference update; foreground refresh retries it before accepting new measurement. If persistence or synchronization fails, controls report the failure and collection remains closed.

Guests use local opt-in and random app-session IDs. Signed-in aggregate-only records contain neither account identity nor account consent revision. IDs identifying private Stash membership/private discovered products are removed from aggregate-only records. New measurement account linkage is stored only under the separate activity opt-in. Optional shopping identity is also consent-locked in legacy click records and merchant facts; activity withdrawal unlinks it without deleting required saves/follows. No anonymous-to-account history stitching, installation fingerprint, raw query, URL, exact coordinate, email, credential, or arbitrary property is added to the telemetry database. Raw session-linked observations are pseudonymous until linkage expires; only later identifier-free rollups may be called anonymous aggregates.

Existing saves/follows/likes/imports remain authoritative transactional records independent of analytics consent. An opted-in account can attach an app-session ID to an existing engagement fact; withdrawal clears that optional context without deleting operational save/follow membership. Soft/hard account deletion removes telemetry identity/context and private entity references while retaining unlinked observations. Existing Phase 1 actor erasure still covers transactional engagement. This is deidentification, not a guarantee that public content references are irreversibly anonymous.

## Event taxonomy and exact definitions

All names are version 1. Envelope: UUID event ID, ISO occurrence timestamp, ephemeral app-session ID, allowlisted entity type/UUID/namespace, surface, iOS/Android/web platform, and app version. Server receipt time/source and eligible creator attribution are server-derived. UUIDs identify actions, never people unless separately consented account linkage is present. Extra fields/properties are rejected. Events are accepted up to 24 hours late and at most five minutes ahead.

- `session.started`: foreground app activity after 30 minutes of inactivity, once per app session. **This is an app usage session, never a playback session.** No additional properties.
- `collection.impression`: at least 50% of the collection card/frame in a conservative content viewport for one observed continuous second while foreground and focused. Feed measurement observes the existing collection frame, not its embedded video. No properties.
- `collection.opened`: successfully loaded collection/focused-collection route, deduplicated per entity/surface/app-session. No properties. Existing navigation/feed-activation counters remain separately labelled legacy recorded views.
- `product.impression`: the same qualified card rule, with catalog/discovered namespace. Collection attribution requires a matching stored product tag. No properties.
- `product.opened`: a successfully rendered Product Page, deduplicated per entity/surface/app-session. No properties.
- `place.impression`: qualified Stash card exposure; canonical place and private save/lead identities stay distinct. No properties.
- `place.outbound_requested`: the existing place Search button invokes its existing destination action. Property: `destination_kind=search`. It is not a place-detail open, destination arrival, or visit.
- `creator.profile_opened`: successfully loaded public profile, deduplicated per entity/surface/app-session. No properties.
- `search.results_served`: server-authoritative first-page typed-results response. Properties: `matching_count`, `fallback_count`, `latency_ms`, `query_length_bucket`, explicit `filter_keys`, `retrieval_mode`. Counts describe returned first-page cards, not total index matches. Debounced typed searches are labelled as such; they are not keyboard submissions. Autocomplete, internal recommendation searches and pagination are excluded. No search text/hash is stored.
- `search.result_clicked`: result selection linked to an acknowledged measured response. Properties: request UUID, result type and zero-based rank. Server verifies returned membership, rank, app session and account linkage before acceptance. Only the measured first page is covered; clicks from other pages are not invented.
- `merchant.outbound_resolved`: successful server destination resolution for catalog or discovered products. Properties: measurement request UUID, destination kind, affiliate boolean. The measurement UUID is separate from transactional click IDs to avoid linking aggregate-only activity to an account through a legacy record. It is not proof of merchant navigation, purchase or revenue.

Client observations are client-measured, not proof of attention. Merchant/search response events require server authority. Explicit save/unsave/follow/unfollow/like/unlike history stays in existing engagement facts; Stash/import membership stays in its own domain. Automatically extracted place/product membership must never be relabelled as a deliberate save.

## Definitions for subsequent reporting

Counts use accepted immutable event IDs. Impression/open counts follow the deduplication above; they are not unique people. Revisits require an opted-in account to have a later qualifying observation in a different app session within a declared supported lookback. Anonymous app sessions are not unique users. DAU/cohorts must disclose the account-measurement population and require the later activity-day summaries, rather than inferring all users from this sample.

Product exposure click rate requires matched exposure/product/collection/session context; until that relationship is implemented and validated, report outbound requests separately rather than divide unrelated totals. Search zero-match rate is first-page typed responses with `matching_count=0` / measured first-page typed responses, even when fallback cards are returned. Search request click rate is distinct measured first-page request IDs with a valid click / eligible measured first-page requests. Saves/followers are current stocks; acquisitions/removals require actual state transitions. No purchases or revenue are inferred.

Future interest weights may use explicit saves/follows, qualified entity opens/revisits, search selections and outbound intent, with recency, frequency caps, negative/removed preferences and confidence thresholds. Impressions alone are weak evidence. There are no playback-based interest weights, completion charts, watch-time comparisons or replay metrics in any later phase.

## Reliability, storage and operational limits

- Client queue: max 500 observations / approximately 500 kB; 24-hour age limit; one session per batch; at most 25 events; fifteen-second/background flush; original IDs retained across backoff retries; lower-priority impressions dropped first. Storage writes coalesce. Account/revision switches invalidate old queues; sign-out stops measurement before credentials change. Dropped counts are local best-effort diagnostics, not a claimed server-delivery total.
- Server: max 50 events / 64 KiB; strict schemas; bounded hashed-address rate buckets (no retained raw address); immutable UUID deduplication; entity authorization and public creator attribution; bounded post-action telemetry waits. Invalid/ineligible records receive explicit discard IDs, preventing infinite retries.
- Exposure work is one bounded native-measurement loop, up to 16 candidates per 500 ms / 128 pending candidates. It stops while disabled/unfocused/background. Both horizontal and vertical clipping are checked; long observation gaps reset dwell. Dense lists can undercount. These are conservative viewport observations, not proof of attention or complete occlusion detection.
- `analytics_events`: raw retention seven days. Session linkage (including optional context on engagement facts), search-response result sets and correlation IDs expire after 24 hours. Optional merchant account linkage in engagement facts/legacy click rows expires after seven days; minimal authoritative business facts/counters remain. `analytics_health_daily`: aggregate operational counts retained 90 days. No raw search results text is retained; the short-lived result set contains only public result IDs/types/ranks.
- `analytics_preferences`: server-only account settings/revision. Withdrawal strips optional identity/session context and private entity IDs; account deletion also removes preferences.
- New tables and functions deny direct anon/authenticated-role access; authenticated APIs derive identity from verified Supabase sessions. The trusted backend mediates all reads/writes. No creator/admin raw-activity endpoint is added.
- Accepted/duplicate/ineligible counts commit with ingestion. Invalid-batch, rate-limit and write-failure diagnostics are minute-buffered best-effort counts, separately labelled by units; they are not a complete delivery guarantee.
- Existing functional search recent/trending caches remain in process memory; they are not the new analytics source of truth. Query text was removed from their analytics logs, and the new click client does not send raw query text to the legacy telemetry endpoint. External HTTP access-log query/header redaction remains a deployment concern.

A revised sizing assumption is 50 observations/DAU/day, excluding playback: 50k / 500k / 5m daily observations at 1k / 10k / 100k DAU. At an assumed indexed 0.6–1.2 kB/row, seven-day raw storage is about 0.21–0.42 / 2.1–4.2 / 21–42 GB. These are planning estimates, not measured traffic or a free-tier guarantee; WAL/backups/rollups are additional. Before 10k/100k scale, benchmark retention/rollups, tune trusted edge rate controls and coalesce low-value aggregate impressions. No infrastructure is purchased by this implementation.
