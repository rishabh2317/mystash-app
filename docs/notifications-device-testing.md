## 2. Feature flags

The client and the server are gated independently. **Both** must be on for a
push to arrive; either alone is harmless.

### Client (inlined into the JS bundle at bundle time)

| Variable | Needed for push | Current local `.env` | `eas.json` |
| --- | --- | --- | --- |
| `EXPO_PUBLIC_NOTIFICATIONS_ENABLED` | `true` | unset (off) | `development`, `preview`: `true`; `production`: unset |
| `EXPO_PUBLIC_PUSH_ENABLED` | `true` | unset (off) | `development`, `preview`: `true`; `production`: unset |
| `EXPO_PUBLIC_EAS_PROJECT_ID` | fallback only | unset | — |

`pushSupported()` additionally requires a physical device, iOS/Android and a
project id. A **development build loads JS from your local Metro server**, so
the `eas.json` `env` only affects the embedded build; for dev-client testing
start Metro with the flags:

```bash
EXPO_PUBLIC_NOTIFICATIONS_ENABLED=true EXPO_PUBLIC_PUSH_ENABLED=true npx expo start --dev-client
```

Check: with the flags off, Settings → Preferences shows no push row, no prompt
appears after publish/follow, and nothing is registered.

### Server (notification worker)

| Variable | Default | Effect |
| --- | --- | --- |
| `NOTIFICATIONS_PUSH_ENABLED` | unset → off | Off unless exactly `true`. Off: no deliveries are created and no dispatcher or receipt poller runs. Registration routes still accept tokens. |
| `EXPO_ACCESS_TOKEN` | unset | Required when the flag is `true`; the worker refuses to start without it. Server-only. |

Neither variable is set in `backend/.env` today, so delivery is disabled.
**Leave it that way until you explicitly decide to test delivery.**

### Which database the test touches

Registration writes `push_registrations` rows through whatever backend
`EXPO_PUBLIC_MYSTASH_INGEST_URL` points at, and that backend's Supabase
project. The app `.env` currently targets `womdeohfpvzmhomgqwig`, which the plan
treats as production. For device testing, point the app and backend at a
non-production project (with the Phase 4 migration and, for offline sign-out,
`20261014120000`) or accept that test registrations land there.
`20261014120000` is **not** applied to `womdeohfpvzmhomgqwig`; against it the
server issues no revocation credential and offline sign-out is local-only.

## 3. EAS and account setup (owner)

1. Decide the final bundle id / package and update `app.json`.
2. `npm i -g eas-cli` (≥ 16), then `eas login` with the Expo account that will
   own the project.
3. From the repo root: `eas init`. It creates the project on expo.dev and
   writes `expo.extra.eas.projectId` (and `owner`) into `app.json`; commit
   that change.
4. iOS (requires a paid Apple Developer Program membership):
   - `eas device:create` and open the link on each test iPhone to register its
     UDID for internal distribution.
   - Enable Developer Mode on the iPhone (Settings → Privacy & Security →
     Developer Mode) after the first install.
5. Build: `eas build --profile development --platform ios` and/or
   `--platform android`. On the first iOS build EAS offers to create the App
   ID, provisioning profile and push key; answer yourself (or decline and
   upload your own key, section 4).
6. Install the build from the EAS link / QR code, then start Metro with the
   client flags (section 2) and open the app.

## 4. Apple APNs key (manual)

1. developer.apple.com → Account → Certificates, Identifiers & Profiles.
2. Identifiers: confirm an App ID for the final bundle id exists with the
   **Push Notifications** capability enabled (EAS creates it on first build if
   you let it).
3. Keys → **+** → name it (e.g. "Mystash APNs") → tick **Apple Push
   Notifications service (APNs)** → Continue → Register.
4. Download the `.p8` (only downloadable once) and note the **Key ID**. Your
   **Team ID** is under Membership details. One key serves sandbox and
   production and all your apps.
5. Upload to Expo: `eas credentials` → iOS → (profile) → Push Notifications →
   upload the `.p8` with Key ID and Team ID; or expo.dev → project →
   Credentials → iOS → bundle id → Push Key → Add.
6. Store the `.p8` in your password manager; never commit it.

## 5. Firebase FCM v1 (manual)

1. console.firebase.google.com → Add project (Analytics optional).
2. Add app → Android → package name = the final Android package → Register.
3. Download `google-services.json`, place it at the repo root, and add
   `"googleServicesFile": "./google-services.json"` under `expo.android` in
   `app.json`. (This file identifies the Firebase app; it is not the sender
   secret.)
4. Project settings → **Service accounts** → Generate new private key. This
   JSON **is** a secret; never commit it.
5. Upload to Expo: expo.dev → project → Credentials → Android → package →
   **FCM V1 service account key** → upload the JSON; or `eas credentials` →
   Android → Google Service Account → Manage your FCM V1 key.
6. Rebuild the Android dev build after adding `google-services.json`.

## 6. Expo enhanced push security (manual)

1. expo.dev → project settings → enable **enhanced security for push
   notifications** (after this, sends without an access token are rejected).
2. expo.dev → account settings → Access tokens → create a token for the
   notification worker.
3. Store it only in the worker's secret store / environment as
   `EXPO_ACCESS_TOKEN`. Do not set `NOTIFICATIONS_PUSH_ENABLED=true` yet.

## 7. Physical-device checklist

Use two test accounts (A, B) and, where possible, one iPhone and one Android
13+ device. "Server row" means the `push_registrations` row for the device's
installation in the **test** database.

Delivery tests (7.3 onwards) need either the server flag switched on by you for
the test environment, or a manual send from Expo's push tool to the device's
Expo push token with data `{"v":1,"nid":"<uuid>","did":"<n>","type":"…","link":"/notifications"}`.

### 7.1 Registration

- [ ] Fresh install, flags on, signed in as A: no prompt at launch.
- [ ] Permission already granted (Android < 13 or re-install): server row bound
      to A, `os_permission = granted`, token fingerprint present.
- [ ] Relaunch within 24 h with nothing changed: no new PUT (row `updated_at`
      unchanged).
- [ ] Flags off build/Metro: nothing registers, no push row in Settings.

### 7.2 Permission grant and denial

- [ ] First publish → explainer appears once → "Turn on" → OS dialog → Allow:
      row registered with `granted`.
- [ ] Fresh install, first follow → explainer → "Not now": no OS dialog; no
      explainer after the next publish/follow.
- [ ] OS dialog → Don't Allow: no further prompts ever; Settings row says
      blocked and opens OS settings.
- [ ] iOS provisional (if applicable) maps to `provisional`.

### 7.3 Receipt

- [ ] Foreground: banner shown once (not twice), inbox unread count refreshes.
- [ ] Background: system notification shown; lock-screen copy is generic for
      account events and quotes no video/Collection titles.
- [ ] Android: notification lands on the expected channel (Drafts and
      Collections, Followers and likes, Account, News and offers).

### 7.4 Taps

- [ ] Foregrounded: tap opens the deep link once; open recorded with
      `deliveryId`.
- [ ] Backgrounded: same.
- [ ] Terminated (swipe app away): cold start lands on the deep link once,
      not twice after relaunch.
- [ ] Malformed/foreign link in data: app opens without navigating there.
- [ ] Tap while signed out: goes to sign-in only.

### 7.5 Sign-out

- [ ] Online: sign out → server row unbound (`user_id` null), presented
      notifications dismissed, badge 0; no push for A arrives afterwards.
- [ ] Offline (airplane mode) with `20261014120000` applied: sign out
      completes locally; server row still bound; SecureStore holds only the
      revocation record (no Supabase token). Reconnect and foreground the app
      (still signed out) → server row unbound, record deleted.
- [ ] Offline without the migration: sign out completes locally; row stays
      bound until the device next registers (expected, documented).

### 7.6 Account switching

- [ ] A signs out, B signs in on the same device: row rebinds to B, A's open
      deliveries are suppressed, nothing of A's is left on screen or badge.
- [ ] A signs out offline, B signs in while still offline, then reconnect:
      A's pending revoke runs first, then B registers; A's stale credential
      cannot unbind B.

### 7.7 OS notification settings

- [ ] Turn notifications off in OS settings, foreground the app: row updated
      to `os_permission = denied`; no deliveries created.
- [ ] Turn back on: next foreground re-registers as `granted`.
- [ ] Android: disable one channel only; other categories still arrive.
- [ ] Uninstall/reinstall: new installation id; old token eventually
      invalidated by a `DeviceNotRegistered` receipt.

## 8. Enabling delivery for a test (owner only)

On the **test** environment's notification worker only: set
`EXPO_ACCESS_TOKEN`, then `NOTIFICATIONS_PUSH_ENABLED=true`, restart the
worker, and check its health report for `push_lag` and `dispatcher_stale`.
Unset the flag to stop.
